# Changelog

All notable changes to the verifier release train are recorded here: the crates under `verifier/` and the `tessera-verify` command-line tool. The verifier is versioned independently of the prover (tags `verify-vX.Y.Z`); the two trains are compatible through protocol versions only ([09 §1](../docs/spec/09-release-and-versioning.md#1-what-is-versioned)). The format follows [Keep a Changelog 1.1](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Fixed

- Check the original cooperative deadline while counting and encoding protocol messages and hashing the public statement in NI/Live drivers (RFC-0019, SP-8, [#182](https://github.com/AbdelStark/tessera/issues/182)). Entry, at most 4,096 primitive writes and completion are checked; cancellation stops nested sequences and fields, returning `ERR-RES-TIME` without releasing partial bytes or a digest. Canonical bytes and transcript ordering are unchanged. Other arithmetic and transcript hashing loops still require hardening.

- Apply the original verification deadline during NI and Live artifact hashing and payload decoding, including cached Live payload replay (RFC-0019, SP-8, [#182](https://github.com/AbdelStark/tessera/issues/182)). Hashes check each 64 KiB block; cursor reads and sequence steps check at most every 4,096 operations, with checks through long ASCII/map comparisons and before returning decoded values. Reader expiry is `ERR-RES-TIME`, never `Malformed`. Live decoding consumes work failures, preserves idle `ERR-PROTO-TIMEOUT` and terminates unexpected messages with `ERR-PROTO-ORDER` as RFC-0036 requires, and counts retained raw frames against its pre-decode allowance. `Cursor::ascii` now returns an owned `String` so validation and UTF-8 conversion can remain chunked without unsafe code; the claim-list reader moves that string without another copy. `ProverMessage` implementations now supply a deadline-aware opening method; ordinary `open` APIs keep their uncancelled behavior. These remain cooperative checks, not hard allocation or I/O bounds.

- Poll the existing driver deadline during Merkle multiproof validation, sibling counting and tree reconstruction, at most every 4,096 work steps and before success (RFC-0019, SP-8, [#182](https://github.com/AbdelStark/tessera/issues/182)). Advice and weight openings map interruption to `ERR-RES-TIME`; uncancelled authentication errors retain their original order. The original `verify_multiproof` API remains uncancelled; `verify_multiproof_with_cancel` adds explicit cancellation.

- Carry the original verification deadline through column-chain hashing, advice/weight coefficient construction, consistency folds, and codeword copy/zero/mask loops (RFC-0019, SP-8, [#182](https://github.com/AbdelStark/tessera/issues/182)). Chained hashes check between blocks and 128-symbol pieces; row loops check at most every 4,096 entries. Cancellation returns `ERR-RES-TIME` without releasing a digest or an accepted opening. Other verifier phases and blocking I/O still require hardening.

- Refine the driver's memory preflight with the derived row coefficients, codeword and NTT twiddles that must coexist for each advice or weight opening ([#182](https://github.com/AbdelStark/tessera/issues/182), SP-8). Use the largest sequential opening, retaining the existing coarse allowance when larger. Checked size overflow and insufficient budget return `ERR-RES-MEMORY` before a Live reveal or opening-buffer reservation. Boundary tests first validate large advice and weight geometries; this remains a partial allocation estimate.
- Poll cancellation during NTT twiddle generation, permutation, butterflies and scaling, at most every 4,096 scalar work steps and at transform completion ([#182](https://github.com/AbdelStark/tessera/issues/182), RFC-0019, SP-8). The driver's advice and weight openings use its original deadline and propagate interruption as `ERR-RES-TIME`. The two explicitly cancellable field APIs may leave partial values; the four original APIs retain their unchanged-input error contract. Other arithmetic, initialization and authentication loops still need deadline checks.
- Open CLI input paths with `O_NONBLOCK` on Apple systems and Linux x86/x86_64, arm/aarch64 and riscv64, then validate the opened handle is a regular file ([#182](https://github.com/AbdelStark/tessera/issues/182), SP-8). A path replaced by a FIFO after preflight now returns `ERR-RES-IO` without waiting for a writer. Other targets retain the earlier preflight behavior; this does not provide hard deadlines for filesystem metadata or regular-file reads.
- Keep one wall-clock budget through NI decoding and verification, and through every Live round, rather than restarting the work clock per message ([#182](https://github.com/AbdelStark/tessera/issues/182), RFC-0019). Recheck it before releasing a seed reveal, column queries or an accepted report. Idle Live expiry remains `ERR-PROTO-TIMEOUT`; expiry during work is `ERR-RES-TIME`. Deadlines within arithmetic loops and hard I/O cancellation remain pending.
- Return typed memory errors when NTT twiddle factors or opening equality tables cannot be reserved (RFC-0019, SP-8, [#182](https://github.com/AbdelStark/tessera/issues/182)). All four `tv-field` transforms reserve scratch before changing their inputs, preserving the unchanged-input error contract; opening checks propagate `NttError::Memory` as `ERR-RES-MEMORY`. Allocator-cap regressions cover both fields, validation precedence and shortages after the opening's persistent buffers.
- Make symbolic schedule point/run construction, coordinate and coefficient copies, literal vectors and reshape metadata allocations fallible (RFC-0019, SP-8, [#182](https://github.com/AbdelStark/tessera/issues/182)). The complete recorded test-small proof previously aborted under sampled allocator shortages; it now returns `ERR-RES-MEMORY`. The separate fuzz workspace runs isolated policy/allocator budget sweeps in CI, preserving the verifier's dependency graph. This does not establish complete production allocation accounting or deadlines.
- Refuse a Live session's startup when its memory policy cannot hold the 32-byte secret share, before entropy or allocation, with terminal `Inconclusive(ERR-RES-MEMORY)` (RFC-0019, SP-8, [#182](https://github.com/AbdelStark/tessera/issues/182)). Counting-allocator checks pin zero allocation on policy refusal or reservation failure and 32 bytes on success. This checks the share only; full session accounting remains pending.
- Bound `tv_cli::run_os` argument collection before converting OS strings, using the same 64-argument and 8 KiB limits as `run`, and catch argument-iterator panics at that public boundary (RFC-0019, SP-8, [#182](https://github.com/AbdelStark/tessera/issues/182)). The binary uses the shared boundary; oversized non-UTF-8 arguments fail the size limit without retaining their contents. Full verifier allocation accounting and arithmetic/I/O deadlines remain pending under #182.

- `tv-core::lowering` represents the anchor circuits' graphs and builds them, written from RFC-0006 'Operation set' and its table of shapes, RFC-0066 and RFC-0072 ([#150](https://github.com/AbdelStark/tessera/issues/150), in part):
  - **The IR.** `Op` gains `Sub`, `ConstAdd`, `Sum`, `Slice`, `GatherPublic`, `Bitwise`, `BitDecompose { low, high }`, `BitFn { f: BoolFn }` and `AssertEqual`; `Transpose` takes a `Perm` of one to four axes, so a bit word `[M, 32]` transposes; a node holds up to three inputs. Constants hold one value or several, one per channel or a gather's indices: `Graph::constant(index)` reads constant `index`. `Graph::constants()` is every constant's values, flat, which is indexed by constant only in a lowered graph, all of whose constants are one value; its documentation says so, and the verifier's tests now read constants by index. `Role::Input(k)` names a builder's inputs. A graph may have no sequence, checkpoint or residual route.
  - **`GraphBuilder`.** Declares public and advice inputs, weight-committed inputs, constants, shift-class sets, the anchor's tables (`AesSbox`, `Gf256Mul { c }`, `Bitwise8 { op }`, an equal kind sharing its id) and checkpoints; then adds nodes, each checked in a fixed order: arity, dangling inputs, output shapes, output kinds, then the operation's own rules. Every broken rule is `BuildError::Declaration { rule }` or `BuildError::Node { node, rule }`, with `Rule` naming one of 25 rules, and nothing is added. `GraphBuilder::extend` appends to a lowered graph. A `Capacity` (tensors, nodes, constant values), counted by the caller, is reserved at once and bounds every collection (RFC-0019 'Robustness'): `BuildError::Capacity`, or `Memory` when it cannot be reserved. A node is built whole before the graph changes. The builder checks shapes and kinds, not meaning: only the verifier's own circuit builders drive it, never a graph the proof or the statement describes (SP-7), and its capacity comes from sizes the statement's maximum and the local resource limits already bound.
  - **Refusals until their slices land.** Range analysis (`RangeError::Unsupported { node }`), gadget selection and the gadget plan (`ClaimsError::Internal`), the schedule (`ScheduleError::Unsupported { node }`, before its layers are read), the token axes (`AxisError::Refused { node }`) and the advice layout (`ClaimsError::Internal`) refuse a graph holding any of the new operations, a `ConstMul` by a constant per channel or a `TableMap` into an anchor table, at the first such node. Each `match` on `Op` lists every operation; none accepts a new one through a wildcard.
  - **Llama unchanged.** The lowering vectors, the schedule vectors, the stage, driver and tamper-corpus tests pass as before. The two test references that evaluate a lowered graph gain an arm that refuses the new operations.
  - **Tests.** Every rule broken alone in a call whose honest twin passes, with the exact error and the graph unchanged; the order of the checks; a SHA-256-shaped fragment and an AES-shaped fragment built from the RFCs' text and read back; a graph built twice is equal; each of 12 new operations appended to a lowered graph refused by each of 9 checks with its typed error, where an appended `Add` passes them all. 14 faults planted in the builder and the refusals were each caught.
  - **Second review** (approved with changes): cases for the rules no test broke alone, `MatMulAct`'s leading axes and rank (`[2, 4]·[4, 6, 1]`), `Rotate`'s odd width, the node bound alone (`AssertEqual` makes no tensor), each of `extend`'s bounds alone, `SoftmaxRow`'s and `RsqrtRow`'s output kinds and the honest `κ = 31`; each of the reviewer's 9 surviving mutants, and 5 more of `extend`'s bounds, is now caught.

- `tessera-verify`'s log lines, its `verify{proof_digest}` and `check{kind}` spans, and `verify --run-manifest PATH`, written from 05 §2 'The verifier's lines', §4, §5 'The verifier's spans' and §6 'The verifier's manifest', 02 §2 and §2.3, RFC-0019 'Check order', RFC-0003 'Envelope' and the `log-event-v1` and `run-manifest-v1` schemas ([#446](https://github.com/AbdelStark/tessera/issues/446)):
  - **Why.** The verifier's only trail was its `tessera.verdict/1` report, whose per-check durations stay null, and the prover's logging cannot be shared with it (RFC-0001). No crate is added: `tv-cli` writes both log formats and the manifest by hand, as it writes its reports.
  - **Observation in `tv-core`.** `tv_core::observe`: `CheckKind`, RFC-0019's thirteen checks with their steps and the verdict report's names, which that report now takes from it; `CheckOutcome` (`pass`, `not_applicable`, `reject`, `inconclusive`); `CheckEvent`, with the check's measured duration; and the `Observer` trait, implemented by `()` and by `Vec<CheckEvent>`. Every entry point has an `_observed` twin: `verify_non_interactive_observed`, `verify_non_interactive_bytes_observed`, `open_live_observed` and `LiveVerifier::{start, on_round1, on_round2, on_round3}_observed`. Each reports the checks it runs, in order, once each, the last carrying the call's outcome; step 5 is `not_applicable`. The unobserved entry points are the observed ones with `()`, so verdicts, the check order and the deterministic report are unchanged. In live mode each `on_round` call reports steps 1 to 6, 10 or 13, as the driver checks every message afresh; `start` reports step 2. The module documentation maps each step to the driver's code.
  - **Options.** Every command takes `--log-format {human,json}` and `--log-level {error,warn,info,debug,trace}`, `info` by default, read before the command's other options and removed from them: a refused option is logged in the format asked for, and an invalid, missing or repeated value of either is refused in the human format, for the command `tessera-verify`. An argument that is not UTF-8 is refused as before, ``unknown command `invalid-utf8-argument` ``, but in the format the valid arguments ask for: `main` now calls `tv_cli::run_os`, which keeps their `--log-format`, `--log-level` and `--json`.
  - **Events.** `tessera.tv_cli.command_failed` (error) for every refusal `command_error` writes, `tessera.tv_cli.check_completed` (debug) for each check that runs, inside `verify` and `check{kind}`, and `tessera.tv_cli.verified` (info), which ends `verify` and `live` with the final status, code, exit code and duration. The human lines are today's at the default level, `error (CODE): detail` and `verify: completed in N ns; protocol/1, anchor/ledger/ZK unchecked`, and none under `--json`; `--log-level debug` adds `debug verify{proof_digest=…}:check{kind=…}: step N outcome in D ns`. The JSON lines are `tessera.log-event/1`, with `ts` in UTC to the microsecond and `target` `tv_cli::log`, with or without `--json`. Lines reach stderr when the command ends, each with the time of its event: a check's is when its last report arrived, not when its line is written. The CLI's own reading, decoding and pinning of the inputs is step 1, joined with tv-core's step 1, and a parameter set it does not accept is step 2's rejection; in live mode a message's decoding joins the driver's step 1 for it. `proof_digest` is the NI proof's envelope digest once its envelope verifies, which `verify` now checks before decoding the payload.
  - **Run manifest.** `verify --run-manifest PATH` writes a public-class `tessera.run-manifest/1` atomically, after the report, so its exit code is final: the build (`tool`: the version; the commit, the build-time variable `TESSERA_GIT_COMMIT` when it is 40 hexadecimal digits, else null; the profile, `release` when debug assertions are off; the test features the build enables, `tv-core/test-params` when it accepts test parameters, else none) and `toolchain.rustc`, the build-time variable `TESSERA_RUSTC_VERSION`, else null. A release build sets both, as the release checklist says, since RFC-0001 refuses a verifier build script (`cargo xtask check-isolation`); other builds record null. `tv_core::TEST_PARAMS` says whether the build has `test-params`; the host, from `/proc` on Linux and `/usr/sbin/sysctl` on macOS, each read up to 4 KiB (a file keeps its complete lines within that, and a `sysctl` answer longer than that is null); the command line; the claim list's parameter set; the three inputs with their envelope digests once each envelope verifies; the report once written; one `tessera_verifier_seconds` histogram sample per check that ran; and the exit and error codes. A `PATH` that names an input or `--out` is `ERR-USAGE` before verification, and then neither file is written; so is a `PATH` that differs from `--out`, or from an input, only in ASCII case in one directory, which a case-insensitive filesystem would make one file. `--out`, and every other command's output, keeps its rule from before #446: refused when it resolves to an input. A `PATH` in a directory that does not exist is `ERR-RES-IO`, also before verification. Once the report is written, a `PATH` that now resolves to it (a link, or a name the filesystem folds, such as Unicode case or normalization) is not written: stdout's verdict becomes `Inconclusive(ERR-USAGE)`, and the report stays; a manifest that cannot be written makes stdout's verdict `Inconclusive` with the write's error, and the report already written stays.
  - **Tests.** In `tv-core`, every case of the SC-4 tamper corpus, NI and live, judged through the observed entry points the CLI calls: the verdict is the unobserved one byte for byte, and each call's checks are steps 1 to `k` in order, the last carrying the verdict (the corpus decides at nine different steps); an observed acceptance reports exactly its report's checks; and the integration tests' first errors end at their deciding steps, live included. In `tv-cli`, the human lines byte for byte, every JSON line against the schema's keys, types and timestamp shape, each event's level, fields and substituted message, level filtering in both formats, a refusal in JSON before and after the command, invalid log options refused in human form, the spans' fields, and the manifest's every field, its features in a plain build and in one with `tv-core/test-params`, path collisions, an unwritable path, a report write that fails before it, and inputs that fail before or after their envelope verifies. In every build, the CLI's log of tv-core's own checks (a claim list resealed under `ni-100/1`, which tv-core stops at step 3 or 4). With `tv-core/test-params`, which CI also runs tv-cli's tests with, a live session through the CLI whose prover, a test thread, replays the corpus's recorded messages under the verifier's session id; a plain build checks only its step-2 refusal. Also each line's time of event, manifest paths that differ only in case from another file, a manifest path that aliases the report once it is written, a non-UTF-8 argument through the library and the binary, operator text escaped end to end, and the host probe's caps. Thirty-one planted mutants, among them a wrong step number, a dropped check, swapped outcomes, a changed human line, a level filter off by one and the manifest written before the report, each fail a test.

- The verifier's pending coin toss, kept across restarts between its commitment and its reveal, written from RFC-0067 'The pending toss', 02 §2.3, 03 §5 and 05 §3 ([#529](https://github.com/AbdelStark/tessera/issues/529)):
  - **Why.** The share `s_V` lived in memory only, and the prover answers one commitment per manifest, so a verifier that stopped between the commitment and the reveal lost the period's audit.
  - **The artifact.** `tv_core::audit::VerifierToss`, schema `0x0702` version 1, `.tvt`: TCE `manifest_digest`, `policy`, `commitment`, then the 32-byte `share`, in RFC-0003's envelope. `open` and `decode_payload` check the envelope (`ERR-CODEC-*`, `ERR-CODEC-DIGEST` for a digest that does not match), then refuse a commitment that is not `H("coin-commit", share)` with `ERR-PROTO-COINTOSS`. The share is secret-class: it stays on the heap, read straight into a buffer cleared on drop, its encodings come back in `Zeroizing` buffers, and no `Debug` of `VerifierToss`, `AuditToss` or `TossFile` shows it. `AuditToss` now holds a `VerifierToss`, and `AuditToss::from(VerifierToss)` resumes a toss read back from its file.
  - **The file.** `tv_core::audit::TossFile`. `commit` draws the share and writes the toss before the commitment can be read: a synced temporary file of mode 0600, hard-linked into place, which fails with `ERR-USAGE` if anything is at the path, so nothing is replaced, then the directory synced; a toss that would not reopen under `TOSS_LIMITS` (1 MiB) is `ERR-CODEC-LIMIT` before anything is written. `open` reads it under the ledger's path rules, a regular file of one name read without following a link and compared by device and inode (`ERR-USAGE`; a lost toss `ERR-RES-IO`). `reveal` is `AuditToss::reveal`: the manifest must be the window's (`ERR-USAGE`), and the sample is in the ledger's `derived`, the ledger written, before it is returned. `clear`, refused with `ERR-USAGE` until that reveal has recorded the sample, overwrites the file with zeros, syncs it, removes it and syncs the directory, and touches only the file it read, by device and inode (`ERR-RES-IO`). - `LedgerFile` holds its ledger with the kernel's lock on the ledger's directory, in place of the lock file, written from RFC-0067 'One writer' as amended ([#534](https://github.com/AbdelStark/tessera/issues/534)):
  - **Why.** A writer that passed its check before the rename and stalled, while an operator cleared its lock file as stale and a second writer accepted a request, renamed a ledger without that record over it, and the request could be accepted twice (INV-AUD-3). A lock file left by a crash also needed an operator.
  - **The lock.** `LedgerFile::create` and `open` open the ledger's directory, resolved once, and take `std::fs::File::try_lock` on it, `flock(LOCK_EX | LOCK_NB)` on Unix, until the `LedgerFile` is dropped or its process ends, a crash included. A second writer, in another process or in the same one, is refused with `ERR-RES-IO` without waiting, as is a second ledger in the directory. No file holds the lock: removing or renaming files in the directory, or renaming the directory, neither releases it nor lets a second writer in, and no stale lock is left. The directory is opened as the ledger is read, checked by metadata that does not follow a link, opened without following one or blocking, and compared by device and inode, so a FIFO in its place is refused at once. A reader of a snapshot, `read_ledger`, takes no lock. The lock file, its token, `Held::remove`'s window and the operator's step for a stale lock are gone. Off Unix no directory is locked, as none is synced: the guarantees are Unix's.
  - **Before each rename** the ledger must still be the file the writer last read or wrote, by device and inode, as before, and the directory's path must still lead to the directory it locked, by device and inode: a directory put at its path with the ledger moved into it, the ledger's inode kept, could be locked by a second writer while the first wrote there by name. Either failure is `ERR-RES-IO`, and nothing is written.
  - **MSRV.** The verifier needs Rust 1.89, for `File::try_lock` (09 §2).
  - **Tests.** A writer stalled between its check and its rename, through the write's test hooks, while the operator finds no lock file to delete, renames the ledger, renames the directory and removes the ledger, and a second writer, refused with `ERR-RES-IO` after each by every name the ledger then has and at a free name in the directory, while a reader reads the ledger: the first writer's record is in the ledger, and the second gets in once the first is dropped. A child process, the test binary run again, holds the ledger; this process is refused, also through the directory's new name, and once the child is killed with `SIGKILL` opens the ledger with no operator step. A second `LedgerFile` in one process is refused, for the same ledger and another in the directory, and a ledger in another directory is not; a symbolic link to the directory and a path through `..` share one lock; a ledger replaced by a copy and a directory replaced around the ledger each refuse the write, and the check's place before the rename is pinned by a replacement on either side of it. The tests that spawn a process, these and the FIFO's, are in `tests/ledger_processes.rs`, one at a time: a child holds a copy of every open file description of its parent until it executes its program, and in the unit-test binary a spawn made 5 to 12 runs in 40 refuse a writer just after another was dropped. Four mutants, the lock skipped, the lock released after the open, the inode check dropped and the directory check dropped, with an unchanged baseline and a no-op control, were each caught.
