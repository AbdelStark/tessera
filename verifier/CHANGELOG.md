# Changelog

All notable changes to the verifier release train are recorded here: the crates under `verifier/` and the `tessera-verify` command-line tool. The verifier is versioned independently of the prover (tags `verify-vX.Y.Z`); the two trains are compatible through protocol versions only ([09 §1](../docs/spec/09-release-and-versioning.md#1-what-is-versioned)). The format follows [Keep a Changelog 1.1](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- `tv-core`'s verdicts name a leaf group and the merge (RFC-0054 'Messages', [#454](https://github.com/AbdelStark/tessera/issues/454)):
  - **`TreeLevel { group, level, round }`.** `group` is `h` for group `h`'s levels, `G` for a grouped stage's table batch, and 0 for an ungrouped stage, which every proof is until grouped stages are verified. The JSON payload gains `group`.
  - **`LeafMerge { round }`.** It is `REJ-LEAF-MERGE`, exit 10.
  - **The documents.** 04 §2, RFC-0033's amendment line and `verdict-v1.schema.json` follow. The tamper corpus's 109 `REJ-TREE` cases now expect `group: 0`, from `generate.py`.

- `tv-core::protocol` decodes RFC-0054's messages ([#454](https://github.com/AbdelStark/tessera/issues/454)):
  - **The messages.** `Round1.leaf_groups` (`LeafGroups { token_bits, layer_bits }`), and `TreeProof`'s `groups` (`GroupProof { roots, levels, values, splits }`), `table_roots` and `merge`.
  - **The bound.** More than 14 group bits is `ERR-CODEC-LIMIT` at the struct's first byte.
  - **The rollout.** This verifier checks no grouped stage yet, so the drivers reject any grouping as `Malformed` with `ERR-CODEC-LIMIT`, and an ungrouped proof with a grouped field as `Malformed` with `ERR-CODEC-NONCANONICAL`: `Round1` or `Round2Response` in live mode, `NiProof` otherwise.
  - **Live decoding.** `open_live` opens a prover's live message as RFC-0043 requires: a decoding failure that is the input's fault is `Reject(Malformed)` under the message's own schema, any other `Inconclusive`. `tessera-verify live` now uses it; it used to answer `Inconclusive` for every live message that failed to decode.
  - **The tamper corpus.** The recorded live replay now runs the live verifier's three phases, opening each message through `open_live` only once the phase before it has passed, so each message is judged under its own schema.

- `tv-core` judges the SC-4 tamper corpus: every NI and recorded-Live case in `spec/vectors/tamper/protocol-1.json` must yield its predeclared verdict exactly, and the producer's lookup metadata must match the verifier's own derivation. An ignored sweep changes every value of the recorded Live session in turn and requires that none is accepted ([#135](https://github.com/AbdelStark/tessera/issues/135)).

- `tessera-verify live` now authenticates caller-owned whole-statement/request metadata before a one-shot RFC-0014 directory exchange. Bounded packet readers, no-overwrite publication, role reuse refusal and challenge causality are covered by independent vectors and actual CLI tamper tests. Full authenticated network transport remains separate work ([#133](https://github.com/AbdelStark/tessera/issues/133)).

- Independent protocol/1 `tessera-verify verify` CLI with caller-owned whole-statement and weight-root pins, exact fixed-point bounds, bounded regular-file loading, atomic input-preserving report output, typed exit codes and schema-checked measured phase context. `tables` independently regenerates the bounded catalog. Real CPU proofs and tampering run through the library and separately built verifier binary in required CI. Live transport, anchor, ledger and audit operations remain explicit future capabilities; test-small proofs certify nothing ([#131](https://github.com/AbdelStark/tessera/issues/131)).

Typed verdicts, exact native-gadget errors and deterministic public JSON include explicit test-parameter/anchor/ledger/ZK boundaries. Real six-case NI/Live integrations, 100 complete replays in each mode and input/report allocation tests cover the accepting path. RFC-0053 is accepted. The current unit is one exact-greedy request; broader batching, full resource hardening and the CLI remain separate work ([#128](https://github.com/AbdelStark/tessera/issues/128)).

- `tv-codec`, the verifier's TCE decoders, written from RFC-0003 without reference to `tessera-codec`. Instead of a trait per type and a derive macro, a cursor reads each primitive, takes and releases depth levels explicitly and checks every sequence length against its element's minimum size before reading an element; composite types are combinators over closures. Every error carries its code (`ERR-CODEC-TRUNCATED`, `-NONCANONICAL`, `-LIMIT`, `-MAGIC`, `-VERSION`, `-DIGEST`) and the offset of the check that failed, in the order of checks the crate documentation specifies; a reader that runs out of memory reports `ERR-RES-MEMORY`, and a schema decoder whose element consumes less than its declared minimum `ERR-INTERNAL`, neither of them a fault of the input. A sequence never has room for more elements than the bytes left can hold (INV-TCE-3), and its room grows with the elements decoded, so sequences nested in one another hold memory in proportion to what they have decoded. Decoding rejects bytes left over (INV-TCE-4) and caps nesting at 256 levels. Envelopes open in RFC-0003's order, with a digest function the caller supplies verified before any payload byte is decoded, and the payload decoder is told the schema version found; `DecodeLimits::MESSAGE` and `DecodeLimits::INTEGER_MODEL` are RFC-0003's defaults. Every vector of `spec/vectors/codec/` passes, every check has a test asserting its code and offset, and 1.6 million decodes of seeded random and mutated inputs, through every decoder and the envelope, run without a panic, each accepted input judged by oracles written from RFC-0003 alone: its canonical encoding computed from the value (INV-TCE-2), its limits, and the offset at which each of its prefixes is cut short ([#44](https://github.com/AbdelStark/tessera/issues/44)).

- `tv-hash`, the verifier's hashing, written from RFC-0004, RFC-0014, RFC-0015 and RFC 9162 without reference to `tessera-hash` ([#52](https://github.com/AbdelStark/tessera/issues/52)):
  - It takes no hash crate: BLAKE3 and SHA-256 are written in safe Rust from the BLAKE3 specification and FIPS 180-4, and `blake3` and `sha2` leave the allowlist (RFC-0019 'Dependencies'). `hash` and `DomainHasher` compute `H(domain, ·)` for the 18 domains of RFC-0004, with context keys derived by the compiler. An input longer than a chunk is hashed sixteen chunks at a time, in a layout the compiler turns into vector instructions: about 2.5 GB/s on a 64 MiB input and 1.4 GB/s on 64-byte inputs on one core of an Apple M4 Max, 2.5 and 2.8 times the test kit's reference.
  - `column_digest` chains a column's symbols over row blocks of `B`. `verify_multiproof` checks a canonical multiproof against a tree size from public data. In order, it rejects a size that is not a power of two, an empty opening, unsorted, repeated or out-of-range indices, missing or extra siblings, and any other root. It allocates nothing: it counts each level's siblings from the indices, then climbs from leaf to leaf, where the prover builds the tree level by level.
  - `Transcript` replays RFC-0004's transcript: `SessionContext` as TCE, labeled absorbs and squeezes with counter and ratchet, rejection-sampled `Fp` and `Fp2` challenges, and challenge indices. `check_grind` takes the transcript by value, so nothing follows a failed proof of work. A challenge that needs more than 16 squeezes, with probability below 2^-496, is `Exhausted`, which RFC-0004 'Failure modes' now maps to `Inconclusive(ERR-INTERNAL)`.
  - `rfc6962` hashes leaves and nodes with their prefixes and checks inclusion proofs by RFC 9162 §2.1.3.2 for trees of any size. RFC-0015 'Verifier checks' now takes an inclusion proof's tree size and root from the signed manifest and its leaf index from the entry, never from the proof: one proof can verify against one root for several pairs of index and size.
  - Every error is typed, and no input panics. Every vector passes:
    - the 35 official BLAKE3 cases in all three modes;
    - `spec/vectors/hash/` and `spec/vectors/transcript/`;
    - NIST's short, long and Monte Carlo SHA-256 messages and the 98 golden RFC 6962 inclusion proofs, both new under `spec/vectors/`;
    - the codec envelopes, opened with this crate's digest.
  - Every check has a test that violates exactly it, the 16-squeeze bound included, through a stub squeeze source. Multiproofs of sparse trees of up to 2^63 leaves verify, and 70,000 seeded random and mutated proofs get exactly the result of oracles written from the specifications. Mutation runs caught every mutant but 3 equivalent ones.
  - `tessera-hash` checks it against the prover's hashing on seeded random inputs (DEP-2): every BLAKE3 length class against the `blake3` crate, whole and in random pieces; every multiproof the prover opens on trees of up to 4,096 leaves; column digests; and 160 transcript sessions, step by step.
- `verifier/fuzz` gains the `multiproof` and `inclusion` targets, whose oracles predict the exact result of every changed proof by recomputing its root their own way, seeded from the hash and RFC 6962 vectors, and `tests/hash_allocation.rs`, which shows that checking proofs, hashing and replaying a transcript allocate nothing. The `fuzz` workflow also runs when `tv-hash` or the hash and RFC 6962 vectors change ([#52](https://github.com/AbdelStark/tessera/issues/52)).
- `tv-core` checks sumchecks, written from RFC-0010 ('Multilinear extensions', 'Tree levels', 'Batching within a stage', 'Sumcheck messages') without reference to the prover's sumcheck code; the crate documentation specifies every check and its order before the code ([#59](https://github.com/AbdelStark/tessera/issues/59)):
  - `reduce` checks the rounds of one sumcheck in the `{0, 2, …, d}` form: each round is present and holds `d` values, is absorbed under `<prefix>/round/{j}`, `p(1)` is derived from the claim, and the next claim `p(r_j)` is evaluated by Newton's forward differences, where the prover may use Lagrange's basis; no round may follow the last. `verify_batch` squeezes `γ` first, batches the claims as `Σ_i γ^i · 2^{n_max − n_i} · c_i`, front-padding smaller instances in their low variables, checks the number of final evaluations, absorbs them, and compares `Σ_i γ^i · g_i` with the last claim, each instance's relation `g_i` evaluated by the caller at its point, the last `n_i` challenges. `verify_product_level` checks one level of the leaf stage's product trees, `Σ_i γ^i · eq(r_i, r'_i) · u_i · w_i`, squeezes `ρ` and returns each instance's claim on its next level at `ρ ‖ r'_i`; its caller joins a tree of height `h` at level `H − h`, and its instances are product trees only, since how a level batches LogUp fraction trees with them is open (RFC-0010 OQ-0010-1). `eq` is RFC-0010's. What the checks return is `#[must_use]`: rounds verify nothing until their last claim is checked, and a level that passed has proven only its next claims.
  - The specification these checks follow is new or rewritten in RFC-0010: 'Tree levels' (pairing, joining heights, the four steps of a level), 'Batching within a stage' (instance `i` enters as `γ^i · 2^{n_max − n_i} · c_i`, padded in its lowest variables, its point the last `n_i` challenges) and 'Sumcheck messages' (the message layout and labels, the order of the final evaluations, and the order of checks with the round each failure reports). RFC-0014's schedule counts indices from 0 and gains `tree/{ℓ}/gamma`. RFC-0013 OQ-0013-2 records that tree levels reveal values its masks do not hide.
  - Errors name the round, counted from 0 as labels count, and whose fault they are: a missing, short, long or extra round, a wrong number of final evaluations and a failed final check are the proof's, `Reject(Sumcheck)` at `rejected_round()`; a degree outside 1 to 7, no instance, an overflowing evaluation count, a relation the caller cannot evaluate, and a challenge that exhausts its 16 squeezes are the verifier's. The crate denies `unwrap`, `expect`, `panic!`, `unreachable!`, unchecked indexing and arithmetic, and `as` conversions; a crate `clippy.toml` exempts `Fp` and `Fp2` arithmetic, as RFC-0019 'Dependencies' says. A hostile proof, with a round of a million values, 131,072 rounds past the last or a million evaluations, makes a check allocate no more than the honest proof of its batch.
  - `spec/vectors/sumcheck/` holds honest proofs from an independent Python prover on the transcript oracle, which pads smaller instances literally and checks every claim, evaluation and tree claim against its definition: products of 1 to 4 tables on 0 to 12 variables and of 5 to 7 tables, batches mixing 3, 7 and 12 variables, batches of `n_max = 0` and of degree 7, and batches of product trees of heights 1 to 6 joined across heights, three of them with a zero leaf, so root 0. Its 62 stages and 39 levels record every challenge, claim, point and transcript state, in 200 KB reproducible byte for byte.
  - Every vector verifies and reproduces every recorded value. Every check is violated exactly once with its exact error, and all 1,496 single-element changes of the vectors' proofs are rejected, each with its predicted error and round: a change to a tree level's `u_i` whose `w_i` is zero passes that level and is rejected by the next, or by the leaf check. A prover that lies in any round, by a constant or in one value, is rejected unless it forges the final evaluations, which then hold a false claim. Seeded random inputs and seeded changes of honest proofs get exactly the result an oracle written from the specification predicts. A mutation run caught all 79 mutants of the checks.
- `tv-testkit` gains a reference sumcheck prover for tests, with its own field arithmetic and its own transcript on the reference BLAKE3, which pads smaller instances implicitly and can lie in a round. `verifier/fuzz` gains the `sumcheck` target, which changes the reference prover's proofs of seeded stages and tree batches and predicts each result without `tv-core`, seeded from the sumcheck vectors, and `tests/sumcheck_allocation.rs`. The `fuzz` workflow also runs when `tv-core` or the sumcheck vectors change ([#59](https://github.com/AbdelStark/tessera/issues/59)).
- `tv-core`'s tests check the product forests of RFC-0010 'Tree levels' ([#58](https://github.com/AbdelStark/tessera/issues/58)). A forest stacks `2^s` product trees of one height, such as SoftmaxRow's rows, the tree index in the high variables. It joins the batch with the claim `Σ_y v_y·eq(r, y)` on its root level, from its public root values `v_y`, at a random point `r`: the last `s` of the challenges its level squeezes under `tree/{ℓ}/root/{c}` before `γ`. `verify_product_level` checks forest levels unchanged, as instances on `s + ℓ − (H − h)` variables. The tests' driver, standing in for the verifier's, squeezes the root challenges and forms the root claims itself, from the RFC text:
  - `spec/vectors/sumcheck/` gains `forest_batches` from the independent Python prover: 4 batches of 11 levels. They hold forests of 2 to 16 trees, SoftmaxRow forests of 8 and 16 trees whose roots are all 0, forests of different `s` and single trees joining at one level, a forest joining late and front-padded, a level where only single trees join while forests are active, and `s_max` up to 4. Every existing value is unchanged, and the file is 282 KB.
  - Every forest batch verifies and reproduces every recorded value: root challenges, entering claims, `γ`, the rounds' challenges and claims, `ρ`, next claims and transcript states. Every claim is its forest level's extension, and every leaf claim the stacked leaves', both computed in the test. All 162 single-element changes of the proofs are rejected with their predicted errors. A non-zero product claimed as zero (21 cases) and a root point of the first `s` challenges are rejected at the level where their forest joins. Exchanged `u` and `w` pass their level and fail the next, or the leaf check. A mutation run of the driver and the vectors caught all 21 mutants.
- `tv-core` checks openings of the advice commitment: RFC-0019 'Check order' steps 9 and 11, written from RFC-0011 'Opening protocol' without reference to the prover's code. The crate documentation specifies every check, its order and its error before the code ([#61](https://github.com/AbdelStark/tessera/issues/61)).
  - **`opening::check_evaluations`.** It first checks the verifier's own inputs: the code length, `1 ≤ P_A ≤ k`, `B ≥ 1`, row indices of at most 64 bits, increasing in range, and the points' lengths. Then it checks the combined rows' shape (`G + 1` rows of `k` values and `P_A` mask coefficients) and each group's claims against its row, `Σ γ·v = Σ_i u_g[i]·eq(column point, i)`. It returns `Evaluated`, `#[must_use]`, the only way to the column check.
  - **`Evaluated::check_columns`.** It takes the queries as drawn, and derives their sorted, distinct set. The answer must hold one column of `N` symbols per distinct index. Each leaf merges its segments' chained digests under `column-merge`, and the multiproof is checked against the root. Then every combined row, the groups' and then `ξ`'s, must agree with every queried column: `Σ c(row)·col_j[row] = enc(u)(x_j) + Z_H(x_j)·M(x_j)`. Rows are re-encoded one at a time, by an inverse NTT on `H`, the mask fold `g = f + (X^k − 1)·M` and a coset NTT on `7·L`.
  - **Errors.** The proof's rejections are `Evaluation` (with the first failing group, or none for a wrong shape), `MerklePath` at the smallest queried index and `Proximity` at the first failing index; they map to 04 §2's `REJ-PCS-*` codes. The verifier's faults are `ERR-RES-MEMORY` or `ERR-INTERNAL`. Every length the proof gives is compared with the parameters or the layout before anything is sized by it.
  - **Vectors.** `spec/vectors/pcs/` holds 10 honest openings and 28 rejections from an independent Python oracle of RFC-0011. Every honest opening verifies with the values the file records on the way, and every rejection gets exactly the oracle's reason, group and column.
  - **Tests.** All 1,311 single-element changes of the honest openings are rejected with the reason the check order gives. A reference prover and oracle written in the tests on the test kit's field and BLAKE3 cover what the file cannot hold:
    - inverse rates 4 and 8, 64-bit row indices, no group, no non-zero row;
    - a false claim behind a combined row adjusted to pass the evaluation check;
    - every draw against codewords changed at a few columns;
    - 3,000 randomly edited openings.

    Hostile lengths of every part of the proof are judged from the lengths alone, and `verifier/fuzz`'s `tests/opening_allocation.rs` bounds what the checks allocate. A mutation run caught all 54 mutants.
  - **Cost.** At production sizes (`k = 2^22`, `n = 2^23`, `5.8×10^5` non-zero rows, 193 queries, 17 combined rows), measured on one Apple M4 Max core:
    - re-encoding: 0.6 s per combined row, about 11 s in all;
    - consistency: 1.2 to 1.3 ns per product, about 2.4 s;
    - leaves: 0.9 s; coefficients: 0.4 s; the evaluation check: 0.5 s.

    The rows are independent, so these parallelize within RFC-0019's performance plan.
- `tv-core` checks LogUp-GKR, RFC-0019 'Check order' step 7, written from RFC-0008 ('Relation', 'Fraction tree'), RFC-0010 'Tree levels' and RFC-0014 'Transcript schedule' rows 4 and 5 without reference to the prover's code. The crate documentation specifies every check, its order and its error before the code ([#62](https://github.com/AbdelStark/tessera/issues/62)):
  - **`logup::check_roots`.** It squeezes `α` and `β`, checks that the roots message holds `n_a, d_a, n_t, d_t` for each instance before encoding it, absorbs it under `logup/roots`, even when empty, and checks each instance in order: `d_a ≠ 0`, `d_t ≠ 0`, then `n_a·d_t + n_t·d_a = 0`. It returns `α`, `β` and the root claims each lookup tree and table tree enters the levels with, `#[must_use]`.
  - **`tree::verify_level`.** One level of the leaf stage, its instances product forests and fraction trees in schedule order. When a fraction tree is present, `λ` follows `γ` under `tree/{ℓ}/lambda`. A fraction tree enters with `p + λ·q`, sends `N_0, N_1, D_0, D_1`, is checked through `eq·(N_0·D_1 + N_1·D_0 + λ·D_0·D_1)`, and moves to `N_0 + ρ·(N_1 − N_0)` and `D_0 + ρ·(D_1 − D_0)` at `ρ ‖ r'`. `verify_product_level` is the same code on forests alone, with no `λ`: every tree and forest level of the vectors, honest or changed in one element, gives the same result and transcript through both. The batch steps it shares with `verify_batch` are split at `γ`, which leaves `verify_batch` unchanged.
  - **`logup::check_leaves`.** It checks that the values message holds one value per instance whose table has values, absorbs it under `logup/values`, even when empty, and checks each instance, the lookup tree first: its leaf numerator claim is 1, then the table tree's leaf denominator claim is `α − t̃(ρ_t)`, with `t̃(ρ_t)` from the caller, its padding rows copies of row 0. - `tessera-verify params` exits 10 (`02 §2.4`, RFC-0051) when any soundness row misses its target (`meets_targets == Some(false)`), while still writing the full report to stdout ([#375](https://github.com/AbdelStark/tessera/issues/375)).
- Check several reading-site claims on `ChannelParams` in `tv-core::weights` (RFC-0052, accepted; RFC-0012 'Opening'; RFC-0036; RFC-0049; [#386](https://github.com/AbdelStark/tessera/issues/386)):
  - `Layout::channel_point` embeds a reading site's weight-type index and zero-pads its channel point to `c_vars = ⌈log2 C⌉`.
  - `Opening` takes `claims: &'a [Claim<'a>]` and `evaluations: &'a [&'a [Fp2]]`: a committed matrix other than `ChannelParams` requires `G = 1`, `ChannelParams` accepts `G >= 1` site claims (checked against `evaluations[g]` with `Evaluation { group: Some(g) }` on the first failure) and re-encodes all `G + 1` combined rows against every queried column, and an empty matrix still requires `G = 0`.
