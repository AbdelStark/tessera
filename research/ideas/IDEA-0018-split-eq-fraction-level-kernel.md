## Mechanism

Setting. A fraction-tree level ([RFC-0008 'Fraction tree'](../../docs/rfcs/RFC-0008-logup-and-tables.md#fraction-tree), the Papini–Haböck level relation [PH23]) reduces a claim `(ñ_ℓ(r), d̃_ℓ(r))` on level `ℓ` to claims on level `ℓ + 1` through one sumcheck of degree 3 over the level-`(ℓ + 1)` tables with the pair bit lowest ([RFC-0010 'Tree levels'](../../docs/rfcs/RFC-0010-proof-schedule.md#tree-levels)): with `n_L(x) = ñ_{ℓ+1}(0 ‖ x)`, `n_R(x) = ñ_{ℓ+1}(1 ‖ x)`, likewise `d_L, d_R`, and `λ` the per-instance combination of the numerator and denominator claims,

```
Σ_x eq(r, x) · [ λ (n_L(x) d_R(x) + n_R(x) d_L(x)) + d_L(x) d_R(x) ]
```

Today's engine (`prove_batch`, EXP-0006's proxy) proves it as three instances `[eq, n_e, d_o]`, `[eq, n_o, d_e]`, `[eq, d_e, d_o]` over `Fp2`, each with its own copy of the `eq` table built in full (`eq_table`, `O(N)` `Fp2` entries) and bound every round, and evaluates every instance at the three nodes `0, 2, 3` of the degree-3 message. Four prover-only changes, none of which alters a byte of the transcript:

1. **Never build or bind a full `eq` table.** Split `eq(r, x) = eq(r_lo, x_lo) · eq(r_hi, x_hi)` over the `n` remaining variables into two tables of `2^{⌈n/2⌉}` and `2^{⌊n/2⌋}` entries ([DT24]; the split point `m ≈ (n − i)/2` of [JoltOpt26]). In round `i` the current variable's factor is the public line `ℓ_i(X) = (1 − r_i)(1 − X) + r_i X` and the already-bound variables contribute the scalar `s_i = Π_{k<i} ℓ_k(r_k)`, updated in `O(1)` per round ([Gru24] §3.2, [JoltOpt26] "EQ polynomial optimizations"). The round sum is an iterated sum: inner over `x_lo` weighted by `eq(r_lo, x_lo)`, outer over `x_hi` weighted by `eq(r_hi, x_hi)`. When a round consumes the last `lo` variable, the `lo` table is re-split from the remaining `hi` variables (its size halves every two rounds; total `eq` work over a level is `O(√N + log N)` entries instead of `O(N)` built plus `O(N)` bound).
2. **Two node sums per round, not three.** Write the round polynomial as `p_i(X) = s_i · ℓ_i(X) · q_i(X)` with `q_i(X) = Σ_x eq'(x) · [λ (n_L d_R + n_R d_L) + d_L d_R](X, x)` of degree 2 (`eq'` the split weights over the remaining variables, `X` the current variable). Compute only `q_i(0)` and `q_i(2)` from the pairs (or `q_i(0)` and the leading coefficient), recover `q_i(1)` from the round claim, `claim_i = p_i(0) + p_i(1)`, so `q_i(1) = (claim_i − s_i ℓ_i(0) q_i(0)) / (s_i ℓ_i(1))` (as [Stwo26]'s `correct_sum_as_poly_in_first_variable` and [JoltOpt26] do; when `r_i = 0`, probability `2^{-128}` over a uniform `Fp2` challenge, the prover computes `q_i(1)` from the pairs instead), extrapolate `q_i(3) = q_i(0) − 3 q_i(1) + 3 q_i(2)`, and send `p_i(0), p_i(2), p_i(3)` as [RFC-0010 'Sumcheck messages'](../../docs/rfcs/RFC-0010-proof-schedule.md#sumcheck-messages) requires: coefficient for coefficient the polynomial the current prover sends, absorbed under `tree/{ℓ}/round/{j − 1}`, the verifier deriving `p_i(1)` from the claim as it does today.
3. **One pair record, one relation.** Interleave the four tables `(n_L, n_R, d_L, d_R)` per pair in one 64-byte record (four `Fp2`), so a pair-round reads one cache line and folds in place, and evaluate the single relation `λ (n_L d_R + n_R d_L) + d_L d_R` per node instead of three instances of a product. With the numerators-1 specialization on the lookup side of the first layer (`n_L = n_R = 1`: `q` at a node needs `d_L d_R`, `λ (d_L + d_R)` and the `eq'` weight, 3 `Fp2` multiplications per pair per node) and the base-field-multiplicity specialization on the table side (`n ∈ Fp`: two `Fp2 × Fp`), as [Stwo26]'s `LogUpSingles` / `LogUpMultiplicities` and [SP1GPU26]'s first-layer kernels do, the generic node costs 5 `Fp2` multiplications per pair per node.
4. **One `eq` structure per batched level.** Instances that have joined a level ([RFC-0008 'Batching'](../../docs/rfcs/RFC-0008-logup-and-tables.md#batching), [RFC-0010 'Tree levels'](../../docs/rfcs/RFC-0010-proof-schedule.md#tree-levels)) share the split `eq` tables and the scalar `s_i` whenever their points coincide (one combined tree per table definition has one point); an instance with fewer variables, front-padded as in ['Batching within a stage'](../../docs/rfcs/RFC-0010-proof-schedule.md#batching-within-a-stage), is constant in the padding rounds and enters the `ℓ_i` factor only once its own variables begin; per-instance `γ^i` weights and the `2^{n_max − n_i}` front-padding scalars stay exactly as RFC-0010 states them (IDEA-0010 mechanism 1, now with the table itself gone).

The verifier's work is untouched: `tv-core` still derives `p_j(1)` from the claim, squeezes `r_j` under `tree/{ℓ}/r/{j − 1}`, and computes its own `eq(r_i, r'_i)` for the final check. Control flow depends on shapes and variable counts only (INV-ARCH-2); `n` and `d` are secret-class and stay inside the kernel, the `√N` `eq` tables are public-coin data.

## Why it could work

- **[DT24] (E0 counts, primary).** On the Spartan shape (two small tables and one `eq`, the same shape as a level with `eq` in `Fp2`) the standard linear-time prover's 8.5N multiplications fall to 6.5N with split `eq` (−23.5%) and to 5N with Gruen's correction (−41%); `eq` memory `O(N) → O(√N)`. Over Goldilocks the saved multiplications are the `Fp2 × Fp` and `Fp2 × Fp2` ones (the `eq` factor is `Fp2`), the expensive kind, so the saving in `Fp`-multiplication equivalents is at least the paper's fraction (SUR-0007 synthesis 1).
- **[DDBDT26] Table 8 (E1, primary; BN254, Apple M4 Max, single thread).** Split `eq` alone 1.26–1.47× on Spartan's outer sumcheck in steady state, 1.76–3.01× when the baseline is memory-bound; the paper's own multiplication count understated the measured gain (SUR-0007 "Where sources disagree"). Other field and other relation: context, not the baseline.
- **[Stwo26] (E0, primary, code read in SUR-0007 and SUR-0002).** Production LogUp-GKR computes the degree-3 round polynomial at `t = 0` and `t = 2` only, recovers `r(1)` from the claim with the `eq` correction (`correct_sum_as_poly_in_first_variable`), shares one `eq_evals` table per round across every instance of the batch, and costs 3 extension multiplications per pair per point for `LogUpSingles`, 5 for `LogUpGeneric` and `LogUpMultiplicities` (two of them base×extension): the node counts of mechanism 3. [SP1GPU26] (E0, primary, code read) keeps first-layer numerators in the base field on GPU.
- **[EXP-0006] (E1, primary; one Apple M4 Max core, rustc 1.95.0, 2026-10-16).** The engine's `eq` tables are 10.3% of the product-tree leaf time (3.27 of 31.7 ns per leaf), and the redundant per-instance `eq` folds are about 8 of the fraction proxy's 107.3 ns per lookup (7.5%); the proxy's 77 `Fp`-multiplication equivalents per lookup exceed SUR-0002's analytic 56–74 because the engine binds the shared `eq` table once per instance and forms three instances' lines separately (observation (b)). The `eq`-table share is measured on the product forest and transferred to the fraction proxy by count (E0): together about 18% of the proxy is `eq` work this idea removes before any node is saved.
- **[SUR-0002] [E0-this] (E0, primary).** The textbook count that sets the `counted` profile's `c_ℓ = 101 ps` carries the `eq` table at 1 of 24.5 `Fp2`-multiplication equivalents and one `eq` fold per layer-round, geometric over rounds and layers, about 2.5–3.5 more: 15–18% of the count, the share split `eq` removes against the cost model. Its node multiplications already assume two points, so Gruen's node saving does not appear against this profile; it appears against the engine (table above).
- **The engine's own fit (E1, primary, EXP-0006 criterion `F`).** `κ × count` predicts the forest within +0.8% to +2.3% and the proxy within 10% (`κ = 1.253 ns` per `Fp`-multiplication equivalent, 77 → 96 ns against 107 measured), so a multiplication count is a usable predictor of this engine's time and the −48% / −58% rows above are not fiction; what they omit is the memory traffic of the pair record and the iterated sum's outer loop, which the experiment measures.

Keys [DT24], [Gru24] and [JoltOpt26] are defined in the source rows of [SUR-0007](../surveys/SUR-0007-sumcheck.md); their bibliography lines are merged by the consolidation agent. [Stwo26], [SP1GPU26], [DDBDT26], [PH23] and [E0-this] resolve in [bibliography.md](../bibliography.md).

## Prior rejection check

Checked against [baseline.md §7](../baseline.md#7-already-rejected), [RFC-0008 Alternatives Considered](../../docs/rfcs/RFC-0008-logup-and-tables.md#alternatives-considered) (one-hot lookups, univariate lookups, base-field challenges, separate trees, shipped tables, floating-point generators) and [RFC-0010 Alternatives Considered](../../docs/rfcs/RFC-0010-proof-schedule.md#alternatives-considered) (layer-by-layer GKR, committing intermediates, per-layer challenges, one monolithic sumcheck, full coefficients): none covers a prover-side `eq` arrangement. RFC-0010 item 5 rejects sending full coefficients and keeps the derived-`p(1)` form, which is Gruen §3.1 and exactly what mechanism 2 relies on, so the specification already leans this way (SUR-0007 "Against the RFCs"). RFC-0008 NG-6 defers "LogUp micro-architecture optimizations beyond the v1 kernels": a scope statement, not a rejection, and one the RFC-0020 v0.1 kernel measurement is meant to revisit. The lookup separation principle [Jo26] is out of scope (it bounds Shout-style one-hot arguments, not the per-lookup sumcheck work of LogUp-GKR). Overlaps: SUR-0007's seed states the mechanism for every level kind and IDEA-0010 mechanism 1 (one `eq` table per batch) is its first part; new here is the pricing on `c_ℓ` with EXP-0006's fraction proxy as an existing E1 harness, the two-point degree-2 inner polynomial for the fraction relation's three products with the numerators-1 and base-field-multiplicity specializations, the interleaved pair record, and the engine-relative operation count. This sweep writes SUR-0007's seed for the product tree as [IDEA-0021](IDEA-0021-split-eq-gruen-level-kernel.md) (lever `c_π`); this note is the lookup half (lever `c_ℓ`, the fraction relation's three products and the fraction proxy as harness). If the consolidation agent merges the two, this note's count and pricing fold into IDEA-0021 as its `c_ℓ` section.

## Kill criterion

In EXP-0006's harness, the split-`eq` two-point fraction level is less than 10% faster per lookup than the engine's current `prove_batch` proxy at 2^21–2^22 entries on the same core, same inputs and challenges (SUR-0007's own killer: `kernel.rs`'s nodes-by-addition loop already makes a node cheaper than a multiplication count suggests, so only the table build and the redundant folds, about 10%, would be real), or, at E2, the saving does not survive a fused GPU layout where the `eq` table was never a memory cost (SUR-0002's 120 B per lookup at eight fused rounds). A measured gain between 10% and 30% against the engine does not kill the idea but refutes the Mechanism table's count and caps the cost-model row at the kill threshold's.

## Cheapest experiment

Hypothesis: a split-`eq`, two-point, single-relation fraction-level prover produces bit-identical round messages and final evaluations to `prove_batch`'s three-instance proxy and runs at most 0.70× its time per lookup on the leaf level (numerators 1) and the generic level at 2^21 entries. Method (E1, `s`, reachable here): add the path to the level prover of `tessera-sumcheck` or to a research copy of EXP-0006's fraction proxy over `tessera-field` (own Cargo workspace under `research/experiments/`, EXP-0006's `Cargo.toml` as the model); rerun EXP-0006's fraction proxy on the same Apple M4 Max core, same seeded inputs and challenges; report ns per lookup for both paths and both levels, bit-for-bit equality of every message checked by a driver around `tv_core::sumcheck::verify_batch` as EXP-0006 does, and `count.py`'s operation split (multiplications, additions, `Fp2`-by-`Fp`) so IDEA-0005's calibration constant `κ` and the fitted `c_ℓ` update. Effort `s` (days), no RFC. Unknown until an H100 run: the GPU share of the saving once the `eq` table is no longer a memory cost in a fused multi-round kernel (the RFC-0020 v0.1 kernel pair, E2), and whether the 64-byte pair record or a structure-of-arrays layout wins on HBM.
