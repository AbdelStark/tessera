## Mechanism

Setting. RFC-0010 'Tree levels' step 2 proves, per instance `i` at level `ℓ`, `Σ_x eq(r_i, x)·Ṽ(0 ‖ x)·Ṽ(1 ‖ x)` by a degree-3 sumcheck whose round `j` message is `p_j(0), p_j(2), p_j(3)`, with `p_j(1) = claim_j − p_j(0)` derived by the verifier ('Sumcheck messages'; this is [Gru24] §3.1). Today's engine (`crates/tessera-sumcheck/src/forest.rs`, "each instance's `eq(r_i, ·)` is built by `tessera_poly::eq_table` for its level"; `kernel.rs`; EXP-0006's reading) builds one `Fp2` `eq` table of `N = 2^{n_i}` entries per instance per level, binds it together with the two value tables after every round, and evaluates three nodes per pair at `k − 1 = 2` multiplications each over the three tables `[eq, even, odd]`.

Prover-only replacement, per instance, three parts:

1. **Split `eq` ([DT24]; [DDBDT26] §6 Lemma 7; [JoltOpt26]).** Never materialize `eq(r_i, ·)`. Write the unbound coordinates of `r_i` as `(r_lo, r_hi)` with `|r_lo| = ⌈m/2⌉`, `|r_hi| = ⌊m/2⌋` for `m` variables left, and keep two tables `eq(r_lo, ·)` and `eq(r_hi, ·)` of `2^{⌈m/2⌉}` and `2^{⌊m/2⌋}` entries plus one scalar `s_i ∈ Fp2` holding `eq` of the already bound coordinates at their challenges (`s_i ← s_i · ((1 − r_{i,j})(1 − c_j) + r_{i,j} c_j)` after round `j` with challenge `c_j`, an `O(1)` update). Round `j`'s node sum is the two-level sum `s_i · Σ_{x_hi} eq_hi[x_hi] · (Σ_{x_lo} eq_lo[x_lo] · V_L(z, x_hi ‖ x_lo) · V_R(z, x_hi ‖ x_lo))`: per pair one product `V_L · V_R` and one scaling by `eq_lo[x_lo]` (`Fp2 × Fp` in round 1, `Fp2 × Fp2` afterwards), exactly today's per-pair multiplications; per `x_hi` group one `Fp2 × Fp2` by `eq_hi`, amortized over `2^{⌈m/2⌉}` pairs. The current variable's own `eq` factor is handled by part 2. When the bound coordinates run past the low half, `eq_lo` is retired and the sum runs over `eq_hi` alone (or the two halves are re-split, as [JoltOpt26] does at `m ≈ (n − i)/2`); either way no table of `N` entries exists and nothing of `eq` is bound per round.
2. **Gruen's correction ([Gru24] §3.2), transcript-preserving ([JoltOpt26]; Stwo's `correct_sum_as_poly_in_first_variable`, [Stwo26]).** With `X` the current variable and `r_{i,j}` its coordinate of `r_i`, `eq(r_i, x) = ((1 − r_{i,j})(1 − X) + r_{i,j} X) · eq(r_{i,>j}, x_{>j}) · s_i`, so `p_j(X) = ℓ_j(X) · v'_j(X)` with `ℓ_j(X) = s_i((1 − r_{i,j})(1 − X) + r_{i,j} X)` public and `v'_j(X) = Σ_x eq(r_{i,>j}, x) V_L(X, x) V_R(X, x)` of degree 2. The prover computes the node sums of `v'_j` at `X = 0` and `X = 2` only (part 1's two-level sum, two nodes), recovers `v'_j(1)` from the instance's own running claim by `ℓ_j(0) v'_j(0) + ℓ_j(1) v'_j(1) = claim_{i,j}`, interpolates the degree-2 `v'_j`, and emits `p_j` at `0, 2, 3` by multiplying by `ℓ_j`. The bytes under `tree/{ℓ}/round/{j − 1}` are the same `Vec<Fp2>` of three values RFC-0010 specifies; the verifier's derivation of `p_j(1)`, its challenge and its final check are untouched. `claim_{i,j}` is the prover's own quantity (`claim_{i,j+1} = p_j(c_j)` per instance, before `γ`-batching; at a forest's root level it is `Σ_y v_y·eq(r, y)` from the public root values, and at every later level `u_i + ρ·(w_i − u_i)` from the level above); a wrong recovery produces a message that fails `p_j(0) + p_j(1) = claim_j` at the verifier, never one that passes. **Degenerate challenges** (added at EXP-0008's pre-registration): the recovery divides by `ℓ_j(1) = s_i·r_{i,j}`, which is zero when the coordinate `r_{i,j}` is zero or when an earlier challenge made `ℓ_k(c_k) = 0`, so that `s_i = 0` and every later message of the instance is zero (each with probability about 2^-128 per round over uniform `Fp2` challenges); the prover then sums the third node `v'_j(1)` from the pairs instead of dividing, and the message `ℓ_j(z)·v'_j(z)` is correct either way. EXP-0008 exercises the fallback by three deterministic cases (a zero coordinate, a coordinate equal to one, a scripted challenge that zeroes `s_i`), each bit-identical to the engine's messages; the branch is on a public challenge (INV-ARCH-2).
3. **Batching as today.** The level's `γ`-batched message is `Σ_i γ^i · 2^{n_max − n_i} · p_{i,j}` (RFC-0010 'Batching within a stage'); each instance keeps its own `(r_i, s_i, eq_lo, eq_hi, claim_{i,j})`. Front-padded rounds, where an instance is constant in the variable, contribute `p_{i,j}(X) = claim_{i,j}/2` as before and bind nothing of that instance.

The operation count against EXP-0006's component split (E0, own count on its 25.5 `Fp`-multiplication equivalents per leaf; three nodes per round in that count):

| Component | EXP-0006 (E0, fitted to E1 within 2%) | After | Why |
|---|---|---|---|
| `eq` tables | 3.0 | about 0.2 | two tables of `√N` entries per instance per level in place of one of `N`; the per-`x_hi` scaling is one `Fp2 × Fp2` per `√N` pairs |
| folds (round 1: 3.5, `Fp2` rounds: 4.5) | 8.0 | 5.3 | two value tables bound instead of three; `s_i` is `O(1)` per round |
| rounds (round 1: 4.5, `Fp2` rounds: 9.0) | 13.5 | 9.0 | two node sums instead of three at the same multiplications per node per pair |
| level build | 1.0 | 1.0 | unchanged |
| **total** | **25.5** | **about 15.5 (−39%)** | |

Additions fall with the node count as well: the engine forms a table's node values by `V(z + 1) = V(z) + Δ` per table per pair (`kernel.rs`), so dropping the node at `3` drops that pass of additions over the three tables and the accumulation of its sums. SUR-0007's accounting from [DT24]'s 8.5N → 5N for the same shape (two value tables, one `eq`) puts the saving at a quarter to a third of the level sumcheck's multiplications, below this count because [DT24]'s baseline already counts fewer `eq` operations than EXP-0006's engine spends. Memory: the per-instance `eq` state falls from `16 N` bytes to `32 √N`, which also removes the 16 B per entry per round the `eq` fold reads and writes (E0, EXP-0006's byte model counts the fused leaf at 40 B per leaf through HBM).

What the mechanism does **not** do: it does not change the degree, the message, the points `r'_i`, the challenge order or RFC-0013's masks; it does not reduce the per-pair multiplications of the product itself (IDEA-0005 and IDEA-0010 mechanism 2 do that and compose with it; [DDBDT26] Lemma 7 is the form in which split `eq` and a window of rounds coexist, so SUR-0007 synthesis 3's round batching composes with it too).

## Why it could work

- **The level shape is exactly the `eq × product` shape the literature optimizes.** [Gru24] §3.2 (E0, primary, full text read in SUR-0007) saves one of `d` node sums per pair per round when the `eq` factor's current variable is pulled out as a public linear factor, for a non-zero sum as well as for a zerocheck. [DT24] (E0 counts, primary) removes the `eq` table and its binding: 8.5N → 5N multiplications (−41%) for the Spartan shape `eq · A · B`, which has Tessera's two value tables and one `eq`; the counted saving on top of Gruen alone is 5.5N → 5N.
- **Measured on real hardware the split beats its count.** [DDBDT26] Table 8 (E1, primary, Apple M4 Max, BN254, single-threaded) measures split `eq` at 1.26–1.47× in steady state and 1.76–3.01× when the baseline is memory-bound; SUR-0007's disagreement note records that the paper's count understated the gain. Stwo ([Stwo26], code read, primary) computes two node sums per degree-3 round and corrects per instance; Jolt ([JoltOpt26], secondary, documentation without counts) ships the split and the Gruen recovery "without changing what is sent to the verifier".
- **On Tessera's side the removable share is measured.** EXP-0006 (E1, primary, one Apple M4 Max performance core, 2026-10-16; standalone forest 31.2–31.7 ns per leaf over three shapes and sizes from 2^18 to 2^22 leaves) puts the `eq` tables at 12% of the predicted leaf time, the folds at 32% (one third of them the `eq` table), the first round at 15% and the `Fp2` rounds at 40%. The share this mechanism removes, at the count's face value, is 12% + 11% + 18% ≈ 40% of the leaf's time; counting the dropped node only against the `Fp2` rounds (the first round's node is cheap: `Fp × Fp` plus one `Fp2 × Fp`) gives 12% + 11% + 13% ≈ 35%, which this note takes as the headline (E0 shares of E1 components). IDEA-0010's mechanism 1 confirmed the `eq`-table share on a second harness (10.3% measured, 11.6% predicted, E1).
- **The saved multiplications are the expensive kind.** Over Goldilocks the `eq` table is `Fp2` while the product tables are `Fp`, so the `eq` fold and the third node's `eq` scaling are `Fp2 × Fp` (2 `Fp`) and `Fp2 × Fp2` (3 `Fp`) products (SUR-0007 synthesis 1, E0): the saving in `Fp`-multiplication equivalents is at least the paper's fraction, where [DT24]'s large-prime-field count treats every multiplication alike.
- **Compute, not memory, binds the leaf stage, so the saving transfers.** EXP-0006's byte model (E0) prices the fused leaf's HBM traffic at 15–63 ps against 45–117 ps of int32 compute on the H100, and on the M4 Max core the leaf cost is flat from 2^18 to 2^22 leaves (E1); a multiplication saved is therefore expected to shorten the pass. The split's own memory saving (two `√N` tables in place of `N`, no `eq` fold traffic) only adds margin on that side.

Keys [Gru24], [DT24] and [JoltOpt26] are defined in the source rows of [SUR-0007](../surveys/SUR-0007-sumcheck.md); their bibliography lines are merged by the consolidation agent. [DDBDT26] and [Stwo26] are in [bibliography.md](../bibliography.md).

## Security gate

| Property | Effect | Pass |
|---|---|---|
| Soundness bits (G-4, RFC-0014) | None. The protocol is RFC-0010's: same degree, same `p_j(0), p_j(2), p_j(3)` under the same labels, same `p_j(1)` derivation, same `r'_i`, same final check `Σ_i γ^i · eq(r_i, r'_i) · u_i · w_i`. The prover computes the same polynomial by another evaluation order; `v'_j(1)` is recovered from the prover's own running claim, so a wrong recovery yields a message that fails the verifier's `p_j(0) + p_j(1) = claim_j`, never one that passes. The soundness bound of RFC-0014 depends on degree and field, both unchanged. | pass |
| Uniqueness upstream of the logits (SP-3, RFC-0009 Lemma 0) | None. No committed value, relation, range or prover-declared quantity changes; the tree's leaves and levels are what RFC-0009 and RFC-0010 define. | pass |
| Zero knowledge (G-5, RFC-0013) | None. Tree levels carry no mask today (OQ-0013-2 records that their round messages are unmasked and leaves the question open, neither better nor worse here); where a stage's masked sumcheck applies, the mask polynomial `G_k`'s round contributions are computed apart from the product's and the split-`eq` kernel does not touch them. `eq_lo`, `eq_hi` and `s_i` are public values derived from challenges (05 §3); secret-class leaves stay inside the kernel. | pass |
| Verifier independence (SP-6) | None. No verifier code changes; `tv-core` keeps verifying the level from the specification (`verify_product_level`, `verify_batch`), and the E1 test uses it as the oracle. | pass |
| Post-quantum (hash-based commitments) | None. No commitment or hash changes. | pass |

Timing: the table sizes, the split point and the round count depend on `n_i` and the schedule, never on a leaf value (INV-ARCH-2 holds). Completeness is the only correctness risk, and the verifier catches it.

## Prior rejection check

- [baseline.md §7](../baseline.md#7-already-rejected): no row covers a prover-only evaluation order of the level sumcheck. The RFC-0009 row rejects cheaper *certificates* and reopens on "a certificate cheaper than one product leaf per score"; this idea keeps the certificate and lowers the leaf's cost, so that row neither covers nor reopens it.
- RFC-0010 Alternatives Considered (layer-by-layer GKR, committing intermediates, independent per-layer challenges, one monolithic sumcheck) and RFC-0018 Alternative 3 (multi-variable rounds, rejected for `(d + 1)^w` message growth) do not touch the prover's evaluation order; this idea sends the same messages and has no multi-variable round. RFC-0010 'Sumcheck messages' already embodies [Gru24] §3.1 (`p_j(1)` derived) and not §3.2, which is what this idea adds, prover-side.
- Overlap with filed ideas: [IDEA-0010](IDEA-0010-shared-point-forest-fusion.md) mechanism 1 (one shared `eq` table per level, 10–12% of the forest's time) is subsumed, since this builds no `N`-entry table at all and so removes the binding as well; IDEA-0010 mechanism 2 and [IDEA-0005](IDEA-0005-base-field-leaf-small-value.md) (small-value and integer first rounds) compose with it, as do SUR-0007 synthesis 3's round window ([DDBDT26] Lemma 7 is split `eq` inside a window) and [IDEA-0009](IDEA-0009-four-ary-tree-levels.md)'s level arity.
- New now: SUR-0007's full-text reading of [Gru24] §3.2, [DT24] and [DDBDT26] §6 with Tessera's `Fp2 × Fp` cost accounting, [JoltOpt26]'s and [Stwo26]'s transcript-preserving form (which answers the objection that Gruen's §3.2 changes the message), and EXP-0006's component split, which prices the removable share on this engine.

## Kill criterion

(1) The E1 kernel pair on the M4 Max (split-`eq` Gruen level prover against `prove_batch` on `[eq, even, odd]` at 2^21 pairs, byte-identical messages) is less than 15% faster per leaf: then the engine's nodes-by-addition rule (`kernel.rs`, EXP-0006) already made the dropped node cheap and only the `eq` part is real, so the idea collapses to IDEA-0010 mechanism 1's size (7.5–12% of the leaf, E1) and its priority with it. (2) The RFC-0020 v0.1 gate shows the GPU level kernel is HBM-bound, in which case multiplications saved do not shorten the pass (EXP-0006's byte model says compute-bound by a factor of about 2–3, E0; E2 decides). (3) The two `√N` `eq` tables per instance per level (`2^11` entries each at `N = 2^22`, 64 KiB of `Fp2` in all) do not fit the shared memory of a streamed tile's level kernel alongside its value tiles, forcing a layout that re-reads them from HBM every round; a shape fact of the RFC-0018 tile plan, settled on paper before any GPU run.

## Cheapest experiment

Run as [EXP-0008](../experiments/EXP-0008-split-eq-gruen-level-kernel/README.md) on 2026-10-16, `done: validated`: `σ` = 42.7–42.8% on the three 2^22-leaf shapes against the pre-registered 20% (validated) and 15% (refuted) thresholds; the level kernel alone 1.596×; the fraction proxy 2.08× / 1.53×.

Hypothesis: on one Apple M4 Max performance core, a split-`eq` prover with Gruen's recovery for the degree-3 level relation over `[eq (public), even, odd]` produces, for every level of each of EXP-0006's three 2^22-leaf forest shapes, transcript states identical bit for bit to `prove_forests`', proofs that `tv_core::tree::verify_product_level` (and `verify_batch` on a `tv-hash` transcript) accept, and runs at least 20% faster per leaf than the pre-registered baseline of 31.2–31.7 ns per leaf (E1, EXP-0006).

Method: in the EXP-0006 workspace (`research/experiments/EXP-0006-product-leaf-cost`: its own Cargo workspace, path dependencies on `tessera-sumcheck`, `tessera-poly`, `tessera-field`, `tessera-hash`, `tessera-codec` and `tv-core`, `tv-field`, `tv-hash`; rule 2), implement `prove_level_split_eq` as research code beside the harness: two `√N` `eq` tables and the scalar `s_i` per instance (part 1), two node sums per round and the recovery of `v'_j(1)` from the running claim (part 2), `γ`-batching as `prove_batch` does (part 3). Seeded synthetic leaves (rule 6). Baseline and candidate in the same binary on the same inputs (rule 4): `prove_forests` at 31.2–31.7 ns per leaf. Protocol as EXP-0006 with its follow-up amendment: 3 warm-ups, 10 measured iterations, each iteration at least 20 ms by repetition, median and coefficient of variation; report ns per leaf and the ratio, and the `count.py` translation of the saving to the H100 interval. Pre-register: `validated` if ≥ 20% faster per leaf with identical transcript states and verifier acceptance on every level; `refuted` if below 15% (kill criterion 1); `inconclusive` between, or if any CV stays above 3% after one rerun. Reaches E1 for the CPU share; the fraction-tree rows stay E0 until the same kernel is tried on EXP-0006's fraction proxy (a second, optional case of the same run). Effort `s` (days, no RFC, prover-only). What stays unknown until an H100 run: whether the level kernel is compute-bound there (kill criterion 2), the shared-memory layout of the two `√N` tables in a streamed tile (kill criterion 3), and the true `c_π` the 73 ps stands for (RFC-0020 gate).

## Refutations

Sweep triage of 2026-10-16: four refuter agents who did not write the idea, one per lens; each argument is condensed from that refuter's verdict, with the cost-model reruns the scoring agent made to check disputed cells noted as such.

| Lens | Verdict | Argument |
|---|---|---|
| soundness | survives | Same argument as IDEA-0018 on the product tree: the verifier's derivation of `p_j(1)` from the claim, the labels and the final check `Σ_i γ^i · eq(r_i, r'_i) · u_i · w_i` are unchanged (RFC-0010:95-99, 108-112), so the prover's evaluation order cannot alter what is accepted and no RFC-0014 term moves; a wrong Gruen recovery fails `p_j(0) + p_j(1) = claim_j`. The `eq` point of each level is `(ρ ‖ r'_i)` from uniform challenges (`tree/{ℓ}/line`, `tree/{ℓ}/r/{j}`) or the uniform root point `tree/{ℓ}/root/{c}` (RFC-0010:87-99), so the division by `s_i · ρ_{i,j}` is degenerate only with probability about 2^-128 per round; unlike IDEA-0018 this note does not name the fallback, which is a completeness obligation to add, not a soundness exposure. A single-tree forest's root level has zero variables (RFC-0010:89), so its first level has no `eq` factor at all and the recovery reduces to the plain `p(1) = claim − p(0)`; front-padded rounds are handled as the note says. ADV-V: `eq_lo`, `eq_hi`, `s_i` are public-challenge data, tree levels carry no mask today (RFC-0013:87, OQ-0013-2), and nothing new is revealed. |
