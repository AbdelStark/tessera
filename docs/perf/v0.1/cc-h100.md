# `c_c` on H100: encoding and column hashing

The committed-element unit cost of [RFC-0020](../../rfcs/RFC-0020-cost-model.md#measurement-protocol-v01-gate), measured on 2026-11-09 with the microkernel of [#55](https://github.com/AbdelStark/tessera/issues/55). The work is rate-1/2 coset Reed–Solomon encoding with a vanishing mask ([RFC-0011 'Encoding'](../../rfcs/RFC-0011-advice-commitment.md#encoding)) and BLAKE3 chained column digests with `B = 32` ([RFC-0004 'Column digests'](../../rfcs/RFC-0004-hashing-and-transcript.md#column-digests)), on rows of `k = 2^22` values with `P = 200` mask coefficients (`ni-100`'s `τ_A`). A committed element is one row value; its codeword has two symbols.

## Result

| Measurement | Median | Min | Max | CV |
|---|---|---|---|---|
| Generate, encode and hash, 4,096 rows (2^34 elements) | 137.47 ps | 137.44 ps | 137.49 ps | 0.01% |
| Generate only | 2.70 ps | 2.60 ps | 2.74 ps | 2.21% |
| Generate and encode | 126.11 ps | 126.08 ps | 126.12 ps | 0.01% |

`c_c` = 137.47 − 2.70 = **134.8 ps per committed element**: encoding 123.4 ps, hashing 11.4 ps. Against the assumed 30 ps, `ρ_c = 4.49`. A second run gave 134.74 ps. Per element and per run, the times are wall times divided by 2^34, with RFC-0020's 3 warm-up and 10 measured runs. Before any run is timed, the benchmark encodes and hashes one block of 32 full-width rows generated on the device. It checks all 8,388,608 column chains against `tessera_pcs::RowEncoder` and `tessera_hash::ColumnChains` on the CPU, and they are equal.

Evidence level E1 on the target hardware: one microkernel on one GPU, not the integrated prover.

### Where the time goes

Per-kernel times for one block of 32 rows, from a CUDA-event harness over the same kernels:

| Kernel | Work | ps per element |
|---|---|---|
| `ntt_pass` (DIF) | the size-`k` inverse NTT's 10 high stages | 19.7 |
| `encode_low` | its 12 low stages, the spread and mask, the size-`2k` forward NTT's 13 low stages | 63.7 |
| `ntt_pass` (DIT) | the forward NTT's 10 high stages | 40.0 |
| `column_step` | one BLAKE3 `column-step` per column over 32 rows | 11.3 |
| device copy, for scale | read and write 16 bytes per element | 5.3 |

Hashing is not the problem. At 11.4 ps it is well under the 20 ps that [OQ-0004-1](../../rfcs/RFC-0004-hashing-and-transcript.md#open-questions) asks about. Reducing the hashed volume would save at most 11 ps of the 135. The encoding is the cost.

## Why the encoding costs what it does

The encoding of RFC-0011 is an inverse NTT of size `k` and a forward NTT of size `2k`. That is `k/2 · log k + k · log 2k` butterflies per row, **34 per committed element** at `k = 2^22`. Evaluating the codeword as two size-`k` coset NTTs instead needs 33, so the count is fixed by the code, not by how the transforms are arranged.

A Goldilocks butterfly costs about 2 ps on this H100, and that is the floor. The GPU has no 64-bit multiplier, so each product is built from 32-bit `IMAD.WIDE` instructions, which run at half rate, plus the reduction modulo `p`. Measured in registers at full occupancy, with no memory traffic and no twiddle computation:

| Butterfly arithmetic | ps per butterfly |
|---|---|
| Canonical (every result reduced below `p`) | 2.59 |
| Lazy (any 64-bit representative, canonical on store) | 1.99 |
| Lazy, product in PTX carry chains | 1.97 |
| Radix-8 group with twiddles: one table load per stage, small roots by shifts | 2.83 |
| Radix-8 group, every twiddle a table load (cache-resident table) | 2.39 |

So any kernel for this encoding spends at least `34 × 2.0 ≈ 68 ps` on arithmetic per committed element. Adding hashing gives `c_c ≥ 79 ps`, or `ρ_c ≥ 2.6` on H100, however well the transforms are scheduled. With realistic twiddle handling (2.4–2.8 ps per butterfly), the arithmetic alone is 82–96 ps.

The kernel measured here spends 123 ps. That is close to `34 × 2.8 = 95 ps` of radix-8 arithmetic plus the passes' memory traffic. The memory traffic is about 30 ps at the measured 3 TB/s, and it barely overlaps the compute, because a 64 KiB tile allows only three resident blocks per SM. Overlapping it (asynchronous copies, double-buffered tiles), together with cheaper twiddles, would plausibly bring `c_c` to 95–110 ps (`ρ_c ≈ 3.2–3.7`). Nothing in this report measures that.

### What was tried

| Change | Effect on the three encoding kernels (ps per element) |
|---|---|
| Radix-2 stages, one twiddle load per butterfly, canonical arithmetic (first version) | 176 |
| Radix-8 rounds in registers, padded shared memory, spread fused into the first forward round | 143 |
| Lazy reduction inside a pass | 133 |
| Shift multiplications for `ω_4`, `ω_8` (`2^48`, `2^120`) | 133 (no change) |
| 128-thread blocks, 4-element runs, 2^12 tiles in strided passes, twiddles by table load | 124 |
| Fused tile of 2^11 instead of 2^12 | 124 (no change) |
| Every twiddle a table load | 135 (worse: the 32 MB table does not stay in L1) |

## For the decision

RFC-0020's rule takes the measured ratio: `ρ_c = 4.49` falls in "Stop and redesign" (`ρ > 4`). Two facts bear on how to read it, and the decision belongs to the maintainer at [#66](https://github.com/AbdelStark/tessera/issues/66), once `c_ℓ` and `c_π` are measured:

- **The kernel is not the floor.** A better-overlapped kernel could plausibly reach `ρ_c ≈ 3.2–3.7`, inside "Proceed with re-plan".
- **No kernel reaches the assumption.** RFC-0011's encoding has an arithmetic floor of about 79 ps (`ρ_c ≥ 2.6`) on H100. The 30 ps target cannot be met by implementation work on this encoding and this field. Meeting it needs a change to what is committed or how it is encoded: fewer committed elements (NG-5 small-value commitments), a cheaper code or field arithmetic, or a different rate. The 94 ps count in [research/baseline.md](../../../research/baseline.md) predicted this range.

## Reproduce

On a machine with CUDA 12.8 or later and an `sm_90` or `sm_100` GPU:

```sh
cargo test --release -p tessera-gpu --features gpu --test commit          # bit-exact against the CPU
cargo run --release -p tessera-bench --features gpu --example gpu_unit_costs -- cc
```

The benchmark prints the GPU environment, the CPU check and the statistics above. `--rows N` (a multiple of 32) changes the run size. The tests in `crates/tessera-gpu/tests/commit.rs` cover four things: encoding for `log k` from 1 to 24, with no mask, one coefficient, `P = 200` and `P = k`; column chains with full blocks, a short final block and the 124-row limit; encoding and hashing together; and the refusal of malformed shapes. Breaking the mask's high term fails two of the four tests, and so does permuting one BLAKE3 message schedule entry.
