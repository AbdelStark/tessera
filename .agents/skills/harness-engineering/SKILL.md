# Harness Engineering

A test suite or repository gate is only as strong as the bugs it is proved to catch. In Tessera, harness engineering means two things:
1. **Structural invariants are enforced mechanically by `cargo xtask`**, never left to reviewer memory.
2. **Verification code and tests are validated by planting faults (mutation testing) and independent oracles**, proving that a broken check fails the build.

## The Five Pillars of Tessera's Harness

### Pillar 1 — Mechanical Repository Gates (`xtask/`)

Every repository-wide invariant in `AGENTS.md` has a corresponding module in `xtask/src/` with offline self-test fixtures under `xtask/fixtures/`:

| Gate command | Module | Invariant enforced |
|---|---|---|
| `cargo xtask lint` | `unsafe_code.rs` | `unsafe` forbidden everywhere except `tessera-field` and `tessera-gpu` opt-in modules with `// SAFETY:` comments; forbidden unconditionally in `verifier/` |
| `cargo xtask lint` | `secret_access.rs` | `expose_secret` appears only in files listed in `secret-access.toml`; `#![deny(clippy::disallowed_methods)]` cannot be weakened |
| `cargo xtask lint` | `spdx.rs` | Every `.rs`, `.py`, `.cu`, `.cuh` file carries `SPDX-License-Identifier: Apache-2.0 OR MIT` |
| `cargo xtask lint` | `links.rs` | Every relative Markdown link `[text](path#anchor)` resolves to an existing file and heading slug |
| `cargo xtask lint` | `policy_files.rs` | `LICENSE-APACHE`, `LICENSE-MIT`, `SECURITY.md`, `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md` exist and are non-empty |
| `cargo xtask lint` | `agent_context.rs` | `.agents/skills` and `.agents/workflows` have valid structure and exact symlinks in `.claude/` and `.codex/` |
| `cargo xtask check-isolation` | `isolation.rs` | `verifier/` shares zero code or path dependencies with `crates/`, and every transitive dependency is in `verifier/allowlist.toml` (`RFC-0001`, `SP-6`, `DEP-1..3`) |
| `cargo xtask check-test-features` | `test_features.rs` | `test-rng`, `test-params`, and `unsafe-debug-dump` fail compilation in `--release` builds (`OBS-4`) |
| `cargo xtask check-mask-rank` | `mask_rank.rs` | Every mask row's revealed functionals are linearly independent on the compiled schedule, every secret value of a matrix's pair `β_T` lies outside its other functionals' span, and every revealed tensor has two variables, for each conformance claim list and the 405B claim list (`R10`, `RFC-0013`, `RFC-0065`, #488); `tessera_compiler::schedule::masks` lists what the schedule does not hold yet |
| `cargo xtask check-deps` | `deps.rs` | `cargo-deny` (`0.20.2`) and `cargo-vet` (`0.10.2`) pass on both the root workspace and `verifier/` |
| `cargo xtask check-pr` | `pr_policy.rs` | Every commit carries a DCO `Signed-off-by:` trailer, zero tool/vendor attribution lines, and user-facing changes update `CHANGELOG.md` |

#### Rules When Adding or Modifying an `xtask` Gate
1. **Use `xtask::Fixture` (`xtask/src/lib.rs`) for self-tests.** Every gate module must have a `#[cfg(test)] mod tests` that copies a clean fixture (or creates an isolated temp directory) and asserts:
   - The clean state returns `Ok(())`.
   - Each planted violation returns `Err(...)` whose error message names the offending file path and the invariant violated.
2. **Never scan gitignored build artifacts or follow directory symlinks into duplicate visits.** Use `repo::files` (`xtask/src/repo.rs`), which respects `.gitignore` and inspects `symlink_metadata`.
3. **Make error messages actionable.** Every `bail!` must state *what* failed, *where* (`file:line`), and *why* (the rule or RFC identifier).

Done when `cargo test -p xtask --locked` tests both the passing case and every failure mode of the gate.

### Pillar 2 — Independent Conformance Oracles (`spec/vectors/`)

Both workspaces (`crates/` and `verifier/`) share conformance test vectors under `spec/vectors/`, generated by `spec/vectors/generate.py` (`cargo xtask gen-vectors`).

#### Rules for Conformance Vectors
1. **Independent math**: `spec/vectors/generate.py` must compute reference outputs using Python's arbitrary-precision integers, `hashlib`, or direct polynomial arithmetic—never by invoking the Rust prover binary and dumping its output.
2. **Boundary and adversarial coverage**: every vector suite must include:
   - Valid edge cases (zero-length inputs, `0`, `1`, `p - 1`, `2^32`, `2^64 - p` limb boundaries).
   - Invalid encodings (`valid: false` with the exact expected `error` code, e.g., `NonCanonicalFieldElement`, `TrailingBytes`, `LengthLimitExceeded`).
3. **Determinism check**: `cargo xtask gen-vectors --check` re-runs `generate.py` in memory and fails if any file in `spec/vectors/` differs by a single byte.
4. **Dual consumption**: every vector file in `spec/vectors/<suite>/` must be asserted by a test in the corresponding `crates/tessera-*` crate *and* a test in `verifier/crates/tv-*`.

Done when `cargo xtask gen-vectors --check`, `cargo test --workspace --locked`, and `(cd verifier && cargo test --locked)` all consume and pass the new vectors.

### Pillar 3 — Mutation Testing & Fault Injection (`scripts/mutate.py`)

Passing tests only prove that the tests accept the current code; mutation testing proves that the tests **reject broken code**.

Give the mutation scratch copy its own `CARGO_TARGET_DIR`, separate from normal validation: shared build artifacts can make an unmodified checkout run a mutant binary. Make it a detached `git worktree` of the commit, not a plain copy: `cargo xtask` gates list files through `git ls-files`.

Count a mutant as caught only when its test fails on its own assertion and the code compiled. trybuild prints its cases' expected `error[E…]` lines, so recognize a compile failure by cargo's `could not compile`, never by `error[`.

Use `.agents/skills/harness-engineering/scripts/mutate.py` (or targeted manual mutations) whenever you touch a verifier check, transcript label, range bound, or algebraic reduction:

```sh
python3 .agents/skills/harness-engineering/scripts/mutate.py \
  --file verifier/crates/tv-core/src/sumcheck.rs \
  --cmd "cargo test --manifest-path verifier/Cargo.toml -p tv-core --locked"
```

#### High-Value Mutations to Verify
1. **Relational operators (`==` <-> `!=`, `<` <-> `<=`, `>` <-> `>=`)**: mutating `claim != expected` to `claim == expected` or `val < p` to `val <= p` must kill at least one adversarial test.
2. **Transcript absorb deletion**: commenting out any `transcript.absorb(...)` call must cause a round-trip or transcript-schedule test to fail.
3. **Degree bound off-by-one**: changing `degree` to `degree + 1` in `tv-core::sumcheck` must be caught by the degree-overflow adversarial test.
4. **Loop boundary off-by-one**: changing `0..num_rounds` to `0..num_rounds.saturating_sub(1)` must be caught by the round-count test.

If any mutation **survives** (all tests still pass), you have found one of:
- A **missing adversarial test**: write the test that kills the mutant before committing.
- A **shadowed adversarial test**: its input violates two checks, and an earlier one rejects with the same reason, so the targeted check is never exercised. Make the input violate exactly that check. In #135, zeroing a LogUp root's `d_a` alone also broke the identity `n_a·d_t + n_t·d_a = 0`; zeroing the whole root `(n_a, d_a)` keeps the identity and leaves only `d_a ≠ 0` to reject. Likewise, when a parameter branch tightens a relaxed polynomial identity to a stricter one (such as `eps_log2 == 0` tightening `m_t − m_t^2 = 0` to `m_t = 0` in #160), an omission proof (`0`) still fails the relaxed polynomial at the random point; the adversarial proof must prove the relaxed polynomial itself so disabling the branch accepts.
- **Dead or redundant code**: simplify the code.
- An **equivalent mutant**: one the specification cannot tell apart, such as an event renamed to another valid name. Replace it with a mutant of observable behavior.

Done when 100% of mutations to security-critical checks in the changed module are killed by the test suite.

### Pillar 4 — Fuzzing & Panic-Freedom (`verifier/fuzz/`)

By `RFC-0019` (`SP-8`), every function in `verifier/` must return `Accept`, `Reject(reason)`, or `Inconclusive(error)` on arbitrary untrusted bytes without panicking, allocating beyond `Limits`, or entering an unbounded loop.

#### Rules When Adding Verifier Decoders or Checkers
1. **Static lint enforcement**: `tv-core` and `tv-codec` enforce `#![deny(clippy::unwrap_used, clippy::expect_used, clippy::panic, clippy::indexing_slicing)]`. Extend these lints to every new `tv-*` crate.
2. **Pre-allocation cap check**: before `Vec::with_capacity(n)`, check `n` against the active `Limits` budget *and* against `remaining_input_bytes / min_element_bytes`.
3. **Fuzz target coverage**: register new entry points in `verifier/fuzz/fuzz_targets/` so `cargo fuzz` feeds arbitrary byte slices into both the decoder and the verification state machine.

Done when the target crate compiles with `unwrap_used`, `expect_used`, `panic`, and `indexing_slicing` denied and has a fuzz or property test over arbitrary byte slices.

### Pillar 5 — Soundness Calibration (`F65537`)

Goldilocks ($p \approx 2^{64}$, extension $\approx 2^{256}$) makes accidental false acceptance impossible to observe statistically in a test run ($\approx 2^{-128}$). To test that the soundness equations themselves hold:

1. Parameterize generic protocol checks or write calibration tests over the small prime field $F_{65537}$ ($p = 2^{16} + 1$) where the theoretical soundness error is $\epsilon \approx d / 65537$.
2. Run $M = 100{,}000$ trials of a cheating prover (e.g., false sumcheck claim, forged LogUp multiset, corrupted Reed–Solomon codeword) against random verifier challenges.
3. Assert that the empirical false-acceptance rate $\hat{\epsilon}$ lies within the binomial confidence interval of the analytic bound $\epsilon$ from `RFC-0014`.

Done when empirical cheating success over $F_{65537}$ matches the analytic soundness formula within statistical tolerance.
