# Promote a validated idea

Output: a draft RFC or an RFC-proposal issue that carries a `validated` idea into the repository's decision process, and the knowledge base updated to point at it.

1. **Scope the change.** List the RFC sections that change and the stability tier of each surface ([02 §1](../../../docs/spec/02-public-api.md#1-stability-tiers)); protocol messages, transcript labels, table definitions, parameter sets and verdict semantics are tier A and need a superseding RFC. List every invariant of AGENTS.md the change touches. Done when the list is complete.
2. **Review the soundness** of the mechanism with the `soundness-review` checklist and write the result as the RFC's security argument. An `unknown` left in the idea's security gate blocks promotion until an experiment or a proof settles it. Done when every checklist item has evidence or is marked not applicable with a reason.
3. **Write the RFC draft** `docs/rfcs/RFC-NNNN-<slug>.md` with the next unused number, `Status: Draft`, and the sections of [CONTRIBUTING.md](../../../CONTRIBUTING.md#rfcs): Summary, Motivation, Goals, Non-Goals, Proposed Design, Alternatives Considered (including what the experiment refuted), Drawbacks, Migration / Rollout, Testing Strategy (the experiment's reproduction and the adversarial tests the change needs), Open Questions, References (the idea and experiment notes by path). When the decision needs discussion first, open an issue from the RFC proposal template with the same content instead. Done when the draft exists and every number in it carries its evidence level and a projection label where due.
4. **Update the knowledge base.** Idea status `promoted` with the link; the ledger; the scoreboard projection restated with the cost model and labeled a projection. Done when `cargo xtask lint` passes.
5. **Hand off** to `issue-workflow`: the RFC pull request first, implementation issues after acceptance. Done when the ledger names the pull request or issue.
